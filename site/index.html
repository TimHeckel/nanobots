nanobots

Self-improving agent loops for any GitHub repo. An outer loop triages, dispatches, reviews, and learns; nanobot workers claim cards and build inside a disposable Daytona sandbox, then ship PRs. GitHub is the only state store. When the bots are out of their depth, they summon-human.

curl -fsSL nanobots.sh/install | sh

or npx nanobots-sh init — runs in the repo you want the loop on. init is an agent, so export an OpenAI-compatible endpoint first — the same one your repo will use for the required review, not an extra key:
OCR_LLM_URL · OCR_LLM_TOKEN · OCR_LLM_MODEL. You'll also want a Daytona key before a worker builds anything; init collects and verifies it for you.

Worker execution is always inside a disposable Daytona sandbox; every PR always gets an OCR review before the outer loop will merge it. Neither is optional.

what init does

It's a conversation, not a flag soup. An agent runs the whole setup and talks to you through it.

  • Reads your actual code. It lists your tracked files, opens the ones that matter, and then proposes which parts of your repo an agent should never touch unattended — specific paths with specific reasons, which you edit. There is no canned list of scary-sounding categories to rubber-stamp: "payments" is not a gate, src/billing/stripe.ts is. Files that look like credentials are refused by the reader, so your .env never enters the model's context.
  • Renders the loop into .nanobots/ — prompts, triage rubric, recipes, an append-only learnings log, the Daytona worker controller.
  • Writes GitHub workflows + issue intake forms; scaffolds the Projects v2 board, Priority/Size fields, labels, and a pinned status issue via gh.
  • Creates your GitHub App for you via the App Manifest flow — one browser click — and stores all three credentials itself. Collects your secrets, and proves your Daytona key works by creating and destroying a real sandbox before storing it.
  • Then gets out of the way: the repo is fully self-contained — no runtime dependency on nanobots. Your rubric and recipes are supposed to drift from the templates. That drift is the learning.

The outer loop never writes product code, so it runs anywhere. The worker does — arbitrary build/test commands, a fresh branch, a push — so it always builds inside a disposable Daytona sandbox, created for one item and deleted the moment it's done. npx nanobots-sh run worker works the same from a laptop, a VM cron, or the installed nanobots-worker.yml Actions cron; only the trigger location changes, never where the code actually runs. Run npx nanobots-sh verify daytona once DAYTONA_API_KEY is set, before turning the worker cron on.

Billing is an env var, not a feature: CLAUDE_CODE_OAUTH_TOKEN runs on a Claude subscription; ANTHROPIC_API_KEY is metered; any Anthropic-compatible provider (DeepSeek et al) works via ANTHROPIC_BASE_URL. Mix per runtime — cheap models for workers, a frontier model for the outer loop's judgment.

the parts

outer loop

Never writes product code. Triages every inbox issue against a rubric, writes work specs, dispatches under a WIP cap, reviews and merges PRs, reports each cycle to a pinned issue.

nanobot workers

Claim an approved card, build inside a disposable Daytona sandbox, open a PR with Closes #N. Claude Code shipped; Copilot's coding agent, Codex, or OpenHands can run in the same sandbox contract.

OCR review

Every nanobots:built PR gets a bounded Open Code Review pass on the exact head SHA, run as a normal Actions job — required, not optional. Critical/high findings hold the merge.

surgical autofix (optional)

Set OCR_AUTOFIX_ENABLED=true and eligible findings get exact, mechanically-validated text replacements from a second disposable Daytona sandbox — one repair commit per round, capped at 3 rounds, protected paths always come back needs_human.

learning

Every finished item appends to LEARNINGS.md; distill passes promote durable lessons into the rubric and recipes. The policy docs are the loop's weights; GitHub history is the training log.

summon-human

Hard-gated paths — the ones init read your repo and agreed with you on — are triaged and specced but never auto-dispatched. The bots post one crisp escalation with options and a recommendation, then wait for you.

the plan gate

Nothing is built until a collaborator replies /nanobots start <hash> to a versioned plan comment. The hash covers the plan text, so an edited plan invalidates the approval instead of silently shipping something you didn't read.

per-run credentials

Each run mints a short-lived, repo-scoped GitHub App token, then revokes it. It grants contents:write and deliberately not pull_requests — a leaked sandbox token can push to a branch nobody watches, and that's the whole blast radius. The controller opens the PR because the sandbox structurally can't.

signal capture — the browser extension

A loop is only as good as what reaches it, and the highest-signal bug report is the one filed at the moment someone sees the bug. Click the toolbar icon on any page: it screenshots, then hands you an annotation layer on the page itself — pen, box, arrow, text, with select-drag-resize-rotate on anything you've drawn. Describe it, pick a repo, file it. It lands as a nanobots:inbox issue and the outer loop triages it like any other.

Screenshots go to your own Cloudflare R2 bucket, so your repo stays free of binaries — the issue just links the image. No bucket connected? Reports file as text.

It also carries a repo-aware chat that searches your code and issues before you file, so you find the duplicate rather than open it. Bring your own model — with a separate vision model if your main one can't read images.

The extension knows when a repo isn't running the loop and says so before you file into a void. Its prompt lives in .nanobots/EXTENSION-PROMPT.md, and the outer loop refines that prompt based on how extension-filed reports actually fare in triage. The intake improves itself too.
